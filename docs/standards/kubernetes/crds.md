# Kubernetes CRDs (`bindery.platform/v1alpha1`)

This repo ships Kubernetes Custom Resource Definitions (CRDs) under `k8s/crds/` (and mirrored under `helm/bindery-core/crds/`). Bindery’s controllers treat these resources as the platform control plane.

## Install

```bash
kubectl apply -f k8s/crds/
```

## CRDs (overview)

- `ModuleManifest` (namespaced): a module’s identity and its `provides[]` / `requires[]` contracts, plus scaling/scheduling hints.
  - File: `k8s/crds/modulemanifests.bindery.platform.yaml`
- `Booklet` (namespaced): a “game composition” (set of modules + optional co-location groups).
  - File: `k8s/crds/booklets.bindery.platform.yaml`
- `WorldInstance` (namespaced): instantiates a `Booklet` into a running world; sets `region` and `shardCount`, optionally links to a `Realm`.
  - File: `k8s/crds/worldinstances.bindery.platform.yaml`
- `WorldShard` (namespaced): explicit shard objects for a `WorldInstance` (created/removed based on `WorldInstance.spec.shardCount`).
  - File: `k8s/crds/worldshards.bindery.platform.yaml`
- `CapabilityBinding` (namespaced): resolved dependency edge from consumer → provider (source of truth for runtime wiring).
  - File: `k8s/crds/capabilitybindings.bindery.platform.yaml`
- `Realm` (namespaced): realm-scoped “global modules” shared by multiple worlds.
  - File: `k8s/crds/realms.bindery.platform.yaml`
- `WorldStorageClaim` (namespaced): requests world/world-shard scoped storage; reconciled into a PVC (server tiers) or an external URI (client tiers).
  - File: `k8s/crds/worldstorageclaims.bindery.platform.yaml`
- `ShardAutoscaler` (namespaced): adjusts `WorldInstance.spec.shardCount` based on resource utilization.
  - File: `k8s/crds/shardautoscalers.bindery.platform.yaml`
- `CapabilityDefinition` (cluster-scoped): capability discovery/policy metadata (versions/scopes/features defaults).
  - File: `k8s/crds/capabilitydefinitions.bindery.platform.yaml`

## Generation and drift

These manifests are **not** currently generated wholesale from the Go types. The
relationship differs per kind, and the difference matters when editing them.

- `Realm` and `ShardAutoscaler` are generated by `controller-gen` v0.20.0 and
  reproduce byte-for-byte from `make manifests`.
- The remaining manifests are hand-written and carry **more** validation than the
  markers in `api/v1alpha1/` currently produce: `minLength`, `minItems`, semver
  `pattern` constraints, field `enum`s, defaults, and richer `status` schemas
  (`observedGeneration`, `conditions[]`, `resolvedModules[]`). Several Go types
  say so directly — `Booklet` is annotated *"NOTE: This skeleton defines only a
  subset of fields"*, and `BookletSpec.Defaults` is tagged `json:"-"`.

Running `make manifests` regenerates every kind and will **drop** those
constraints. Review the diff before committing; do not treat the generator as
the source of truth until the Go types have been brought up to parity.

What *is* enforced, on every CI run, is `make verify-crds`:

1. every kind registered into the scheme has a manifest in `k8s/crds/`; and
2. `k8s/crds/` and `helm/bindery-core/crds/` are identical.

Invariant 1 is one-directional by design. `CapabilityDefinition` is applied
declaratively by the sample game and granted in RBAC, but has no Go type and no
controller, so requiring a type for every manifest would flag it wrongly.

Invariant 1 exists because violating it is not a cosmetic problem. `main.go`
registers a controller for every kind unconditionally; if the API server has
never seen that kind, its informer never syncs, and the manager exits on a
cache-sync timeout. A missing `ShardAutoscaler` manifest broke the e2e smoke
test this way while every other check stayed green.

## Example resources

The platform repo intentionally does not ship a “game example” under `k8s/`.

For a runnable sample game, see:
- `examples/booklet-bindery-sample/k8s/`

Suggested apply order (sample game):

```bash
kubectl apply -f k8s/crds/
kubectl apply -f examples/booklet-bindery-sample/k8s/
```

- `bindery.platform/world`
- `bindery.platform/game`
- `bindery.platform/module`
